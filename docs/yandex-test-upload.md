# Публикация тестового Docker-образа в Яндексе — подготовка

Тестовая ветка: `deploy/yandex-cloud`. **Основную ветку `main` и Vercel Production не изменять.**

Подготовлен файл `.github/workflows/yandex-test-upload.yml`. Он **не запускается на push** и требует явного ручного подтверждения `UPLOAD-TEST-IMAGE`. Он проверяет Docker и отправляет в реестр **только образ**, без создания ревизий Serverless Container, настройки триггеров или DNS.

## Важное ограничение GitHub Actions

Новый workflow с `workflow_dispatch` обычно **не появляется для ручного запуска в интерфейсе**, пока соответствующий YAML отсутствует на default branch (`main`). Чтобы соблюсти запрет на изменения `main`, **мы не добавляли туда workflow**. Следовательно, процесс сейчас *подготовлен, но не активирован*. Не следует ожидать появления кнопки «Run workflow» для него.

В дальнейшем можно либо отдельно согласовать узкий безопасный workflow-dispatcher в `main`, либо выполнить загрузку вне GitHub Actions с короткоживущим IAM-токеном через собственную рабочую станцию/Cloud Shell. Не обходить это ограничение несанкционированными изменениями основной ветки.

## Когда согласуем фактическую загрузку

1. Уточнить, какой Docker-реестр будет целевым. Старый `cr.yandex` / Container Registry прекращает работу в декабре 2026; предпочтительно перейти на новый Yandex Cloud Registry до долгосрочного размещения.
2. Проверить расходы на хранение Docker-образа и возможность применить его в Serverless Containers.
3. Назначить отдельной учётной записи только минимальную роль для загрузки образов в **нужный реестр** (для старого Container Registry — `container-registry.images.pusher`).
4. Получить **короткоживущий IAM-токен**, срок действия до 12 часов, и передать его *только* через защищённый GitHub Actions secret `YC_REGISTRY_IAM_TOKEN`, не в чат, код, логи или скриншот.
5. Проверить адрес и ID выбранного реестра; выполнить ручной запуск только в тестовой ветке с подтверждающей фразой. Уникальный tag равен SHA коммита.
6. После проверки загрузки удалить/заменить секрет токена; не давать этому workflow доступ к рабочим Supabase/Vercel.

**Сейчас никакой образ не загружен.** Он проверенно собирается в отдельной GitHub Action, которая не выполняет публикацию.

## Инварианты безопасности

- Dockerfile содержит `DEPLOY_TARGET=yandex-neon-test` и фиктивный адрес Supabase `https://isolated.invalid`.
- Никаких значений `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_URL` рабочего проекта, токена Telegram или `CRON_SECRET` в GitHub Actions.
- Основные API приложения остаются заблокированными через middleware. Режим тестовой авторизации работает только в отдельных маршрутах.
- Не объединять `deploy/yandex-cloud` в `main`, не изменять Vercel Production и не подключать рабочую Supabase.
