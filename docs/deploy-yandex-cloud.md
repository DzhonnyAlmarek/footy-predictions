# Тестовая копия на Yandex Serverless Containers

Эта ветка **не меняет** действующую публикацию Vercel и не содержит автоматического развёртывания. Не объединять её в main только ради тестового запуска.

## Ограничения безопасности

- Не публикуй тестовый сервер открыто до проверки серверных маршрутов на изменение данных (включая вызовы SQL RPC, Telegram и резервные копии).
- Не подключай `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` или токен Telegram на первом тестовом запуске.
- У сайта есть пути записи в рабочую БД через пользовательские запросы; для полноценного тестирования требуется **отдельный тестовый Supabase-проект с копией схемы и обезличенными данными**, либо аудит и режим read-only для всех путей.
- Не создавай Cron-триггеры в Yandex Cloud. Vercel Cron продолжает работать только на основной площадке.
- На тестовой площадке не используйте production-домен и не меняйте DNS основной площадки.

## Сборка

Нужны Docker, Git и доступ к GitHub. В тестовом Dockerfile зафиксированы нерабочие заглушки Supabase: нельзя передавать адрес или ключи production Supabase даже через build-arg.

```bash
git clone --branch deploy/yandex-cloud https://github.com/DzhonnyAlmarek/footy-predictions.git
cd footy-predictions

docker build --pull -t footy-predictions:yandex-test .
```

Проверка локального запуска (после настройки тестового Supabase):
```bash
docker run --rm -p 8080:8080 -e PORT=8080 footy-predictions:yandex-test
```

Для Yandex Cloud: загрузить образ в реестр, создать ревизию Serverless Container с режимом HTTP-сервера, портом из переменной `PORT`, RAM первоначально 512 МБ (при нехватке — 1 ГБ) и минимальным количеством экземпляров 0. Права доступа к реестру и стоимость хранения образов проверить до запуска.

## Что ещё обязательно проверить

- Фактические требования Next.js 15 к переменным окружения во время сборки; выполнить `npm run build` с тестовыми значениями.
- Использует ли код `SITE_URL` и переменные Telegram; выставить отдельный тестовый адрес.
- Доступ к изображению, авторизация, вход, прогнозы, подсчёт очков, админские операции, резервные копии и Telegram. Записи в production Supabase не тестировать.
- Региональное время ответа из РФ, cold start и фактический расход CPU/RAM.

## Статус

Только конфигурация сборки. Docker-образ **ещё не собран и не опубликован**. Для полноценной проверки нужна отдельная тестовая БД и инфраструктура Yandex Cloud.

## Текущий режим защиты (обновление 08.10.2026)

Docker-образ принудительно устанавливает `DEPLOY_TARGET=yandex-neon-test`.
Пока миграция к Neon не завершена, middleware возвращает HTTP 503 для всех
`/api/*` кроме `/api/test/health`, не даёт открыть страницы приложения и
возвращает заглушку на `/`. Это **не** готовая система авторизации.
Проверка `/api/test/health` не обращается к БД.

Не отключайте этот режим и не переопределяйте `DEPLOY_TARGET` в облаке:
это активирует исходные Supabase-маршруты, включая операции записи.

**Перед развёртыванием дополнительно:** убедиться, что при сборке и в
переменных Yandex Cloud отсутствуют адрес и ключи рабочего Supabase.
Настроить отдельный Neon backend, его пользователей, изоляцию API,
CSRF/сессии и безопасное хранение секретов. Затем постепенно открыть
только проверенные маршруты с отдельными тестами. Следует проверить,
что Docker/Next.js сборка проходит: пока это не выполнялось.
