# Footy: замена Vercel/Supabase на Yandex Cloud/Neon

## Область изменений
- Рабочий Vercel, GitHub main и Supabase остаются неизменными до согласованного переключения.
- Эта ветка предназначена только для подготовки. Нельзя разворачивать её как рабочую до завершения проверок.
- Текущая тестовая Neon branch br-snowy-dream-b1z9gj1l содержит экспериментальные данные и не должна стать рабочей базой.
- Neon branch br-autumn-union-b1br9jf2 называется production, но её пригодность для нового сайта ещё не подтверждена. Не изменять её до отдельного решения.

## Блокеры до переключения
1. Реализовать отдельный режим запуска без жёсткой привязки к тестовому URL и тестовому Neon-хосту. Сохранить запрет на случайное подключение к неверной базе.
2. Обеспечить обычные URL входа, кабинета участника, календаря, прогнозов, рейтинга и ADMIN без публичных /test-* маршрутов; тестовые маршруты не должны открывать доступ к рабочим данным.
3. Уточнить, как переносить пароли: старые пароли/хеши нельзя считать совместимыми без проверки. Предусмотреть безопасную смену пароля.
4. Подготовить повторяемый импорт Supabase -> Neon: участники, турниры, этапы, туры, команды, матчи, прогнозы, результаты, бонусы, журнал очков. Проверить ссылки, суммы, дубликаты, идентификаторы.
5. Выполнить финальную синхронизацию после временного прекращения записи в старую систему; сверить данные, прежде чем открывать запись в новой.
6. Создать отдельный рабочий контейнер Yandex Cloud и настройки секретов. Сначала временный адрес и сквозные проверки всеми ролями.
7. Подготовить откат: сохранить доступ к старому сайту и снимок базы. Не допускать двух независимых точек записи после переключения.

## Минимальный сквозной тест
- Вход/выход ADMIN и всех семи участников.
- Создание этапа, тура и матча; видимость участнику.
- Прогноз до дедлайна; запрет изменений после дедлайна.
- Ввод и исправление результата; перерасчёт очков и рейтинга.
- Проверка исторических прогнозов, бонусов, итоговой таблицы и разграничения ролей.
- Рестарт контейнера, health, сохранность сессий и данных.

## Принцип запуска
Сначала тестируем новый рабочий контур на временном адресе, затем короткая остановка записи на старом сайте, дельта-синхронизация, проверка контрольных сумм, переключение адреса и наблюдение. До финальной синхронизации старый сайт остаётся источником истины.

## Уточнение 17.10.2026: параллельная эксплуатация
- Существующий сайт не выключать при запуске нового и до отдельного решения пользователя.
- В период проверки старый Supabase — единственный источник рабочих записей; новый сайт работает на изолированной копии и не принимает независимые реальные прогнозы.
- Перед переключением записи выполнить последнюю синхронизацию и проверку. После переключения старый сайт может оставаться доступным в режиме чтения/резерва, но без независимых записей.
- Финальное отключение старого сайта — отдельный согласуемый этап после успешной эксплуатации нового.
- На проверочной ветке Neon br-late-grass-b14rxtc7 создана схема footy_cutover и выполнено копирование девяти таблиц из migration_source. Контрольные количества совпали, но это не актуальный снимок Supabase и не проверка целостности ссылок.
